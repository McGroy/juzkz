# ЭВГА: требования и постановки по документации фронта `saq-evga-test`

Область отчёта: документация фронтенда ЭВГА (`saq-evga-test/README.md`, `saq-evga-test/docs/**`) и та часть исходников фронта, на которую документация ссылается как на «единственный источник правил» (`src/types.ts`, `src/data/documentMatrix.ts`, `src/modules/evga/workflow.ts`, `documentStateMachine.ts`, `deadlines.ts`, `qualityAssignment.ts`, `caseRules.ts`, `documentFactory.ts`, `src/services/*`). Для раздела «соответствие с prof» прочитаны `saq-prof-control-demo/backend/apps/{core,accounts,documents,cabinet,ersop,cases,subjects}` и `docs/tor/Postanovka_obshhaya` (текстовая выгрузка `prof_docx4/Postanovka_obshhaya.txt`). Для расшифровки кодов документов (М11, М14–М19 и т.д.) использованы `n8n_old/bpmn/bpmn_inventory.txt` и `n8n_old/n8n_export/analysis/*.txt` — только как справочник кодов; полный разбор n8n/BPMN — область другого агента.

Все пути ниже даны относительно `(рабочая папка анализа)/src/`.

## 0. Краткое резюме

1. Фронт ЭВГА — это **тестовый автономный контур**: React 19.1.1 + TypeScript 5.9.3 + Vite 7.1.7, без роутера-библиотеки и без API. Всё состояние (дела, документы, версии, вложения в base64, уведомления, назначения КК, апелляции, третьи лица, календарь) хранится одним массивом `AuditCase[]` в IndexedDB (`saq-evga-test` → store `state` → key `cases`) через контракт `AuditCaseRepository { load(); save(cases) }` (`evga/saq-evga-test/src/services/auditCaseRepository.ts`). Роль пользователя — переключатель в меню (`localStorage["saq.evga.account.v1"]`), «выход» — флаг `sessionStorage["saq.evga.demo.signed-out"]`.
2. Вся бизнес-логика (переходы статусов, зависимости документов, КК, регистрация, доставка объекту, сроки) реализована **чистыми функциями** в `src/modules/evga/*.ts` и покрыта ~212 node-тестами (`tests/*.test.ts`). Это фактически готовая спецификация серверных сервисов: бэкенд в стиле prof должен воспроизвести эти правила в Django-сервисах и отдать фронту те же статусы/строки блокировок.
3. Документация фиксирует **8 ответов заказчика (Q01–Q08)**, которые являются жёсткими ограничениями бэкенда: только последовательное согласование; точный статус «Возвращен на доработку»; документы создаются вручную из меню «Создать»; после замечаний КК создаётся новая версия v2, v1 сохраняется; этапы проходят по очереди через КК; объект планового дела берётся из перечня; аудитор заполняет / согласующий согласует / утверждающий утверждает.
4. Вопросы Q09–Q20 (поручение, доп. поручение, встречная проверка, КК на основном/заключительном этапах, предписание, кабинет объекта, возражения, ответ о принятых мерах, завершение дела, справочники, печатные формы) **без ответов**; команда приняла временные решения, помеченные «Не проверено на прежнем стенде».
5. Каталог документов: 36 видов основного дела + 7 видов встречной проверки + 62 рабочие формы (59 АФО по № 272 и 3 по № 113) = 105 определений форм (`src/data/documentMatrix.ts`, `src/data/workingPapers.json`). Коды М-серии (М5-IPI … M26-TU, M38–M57) фронту неизвестны — он использует свои строковые `kind` (`irpi`, `program`, `instruction`, `account`, …); соответствие восстановлено в разд. 2.4.
6. Всё, что связано с реальными пользователями, ЭЦП/НУЦ, Keycloak, ЕРСОП/КПСиСУ, ГБД ЮЛ/ФЛ, АИС ОИП, ВАП, внешней почтой, печатными бланками, серверной нумерацией — **не реализовано / имитируется** и является предметом бэкенда.
7. В prof-бэкенде уже есть переиспользуемые механизмы: append-only `AuditEvent` (ровно табл. 49 ТЗ), `NumberSequence/IssuedNumber`, generic `Attachment` + MinIO + SHA-256, `User/FederatedIdentity/AuthSession/OidcAuthRequest` (Keycloak PKCE), `Role/RolePermission/RoleAssignment` + `HasDomainLevel`, кабинет субъекта (`IsSubjectRepresentative`, `CabinetAcknowledgeView`), `Acknowledgement` (portal/manual), `ErsopPackage/ErsopExchange`, единый JSON-конверт ошибок, пагинация. Чего в prof **нет**: версий документа, маршрутов согласования с несколькими участниками, назначаемых ролей уровня дела (эксперт КК, подтверждающий КВГА, соавтор), рабочих дней/производственного календаря, уведомлений, двуязычных полей.

## 2. Реконструированная постановка ЭВГА

### 2.1 Границы и этапы

Название: постановка раскрывает ЭВГА как «электронный **внутренний** государственный аудит» (`specification-baseline.md`, `first-flow.md`); экран выхода печатает «Электронный внутренний государственный аудит» (`src/pages/LoginPage.tsx`). Раскрытие «внешний» не подтверждено — в проектной документации использовать «ЭВГА».

Заказчик: КВГА МФ РК (контролирующий орган по умолчанию `КВГА МФ РК`, `first-flow.md`; в demo — `DEMO_USER` «Руководитель рабочей группы центрального аппарата», `src/config.ts`).

| Этап (`Stage` 0/1/2 в `types.ts`) | Сущности и процессы (по `specification-baseline.md`) | КК |
|---|---|---|
| 0 Подготовительный | Предварительное изучение (ИРПИ), программа аудита (соответствие / АФО), план аудита (≥2 объектов), аудиторское задание (≥2 аудиторов), поручение (подтверждение КВГА), дополнительное поручение, уведомление в ВАП, учетная карточка (регистрация ЕРСОП/КПСиСУ), требование сведений, акт о воспрепятствовании | КК1 (`quality1`) |
| 1 Основной | Аудиторский отчёт, реестр нарушений, аудиторские доказательства, еженедельный отчёт, акт контрольного обмера, возражения объекта, результаты возражений (апелляционная комиссия), третьи лица, встречная проверка | КК2 (`quality2`) |
| 2 Заключительный | Аудиторское заключение, предписание, талон-уведомление (ЕРСОП), передачи в вышестоящие/правоохранительные органы/АБП и ответы, иски (4 вида) и решения по искам, ответ о принятых мерах, справка о завершении | КК3 (`quality3`) |

Правило перехода между этапами (Q02 + `workflow.ts:creationBlock`): документ этапа N создаётся только если `audit.quality[0..N-1]` все `true`; `quality[stage]` пересчитывается функцией `qualityPassed` при каждом сохранении (заключение КК активно, решение «Без замечаний», все `qualitySources` этапа утверждены/согласованы, версии совпадают с `sourceVersions` заключения).

Не входит в модуль (по документации): СВА, Профконтроль, административное производство (АПН, коды М38–М42/М48–М53/М57), кабинет юридического блока, оценка деятельности СВА (№ 480), аудит эффективности СВА (№ 873).

### 2.3 Общая модель документа

Постановка: `Проект → На согласовании → Активный`; возврат даёт `Проект` либо `На доработке` (расхождение № 3 журнала); согласование и утверждение — с ЭЦП; карточка содержит вложения, историю, меню техпроцесса; редактирование только автором и соавторами.

**Принятое во фронте** (`types.ts:DocStatus`, 11 значений):

| Статус | Когда устанавливается (файл) |
|---|---|
| `Проект` | создание версии (`documentFactory.ts`), отзыв с согласования (`recallDocument`), новая версия |
| `Направлен на согласование КК` | `sendDocumentToQuality` — проект заблокирован от изменений до заключения КК |
| `На подписании рабочей группой` | задание (`signAssignmentGroup`) и отчёт (`requestReportGroupSignatures`): подписывают все участники версии РГ |
| `На согласовании` | `submitDocument` — последовательный маршрут через `shared/workflow/approvalRoute.ts` (mode по умолчанию `sequential`) |
| `Согласован` | все согласующие приняли; для подготовительных/основных документов окончательное утверждение отдельным проходом после КК |
| `На подтверждении КВГА` | поручение/встречное поручение (`sendInstructionToKvga`) |
| `На подтверждении реестра` | реестр нарушений (`sendRegistryToConfirmer`) |
| `На утверждении` | последний шаг маршрута (утверждающий / signer) |
| `Возвращен на доработку` | Q05; `returnDocument` (комментарий обязателен), возврат ЕРСОП (`performRegistration(action="return")`) |
| `Отклонен` | `rejectDocument` — терминальный для версии; новая версия только явно |
| `Активный` | утверждение; `activateDocument` для `directActivation`-видов; отчёт становится активным при отправке объекту (`deliverDocument`) |

Версии: `AuditDocument.versions[]`, `activeVersion(doc)` = последняя; `createNextVersion` разрешён из `Активный | Направлен на согласование КК | Согласован` (Q07: v2 после заключения КК); `createReturnedRevision` / `createRejectedRevision` — из возврата/отклонения; предыдущие версии, их подписи, вложения и маршруты (`approvalRoutes` со статусом `superseded`) неизменны. Заключение КК хранит `sourceVersions[{documentId, version}]` и действует только для этих версий.

Права редактирования (`documentStateMachine.ts:canEdit`): статус `Проект` или `Возвращен на доработку`, роль = `ownerRole` версии (`auditor` по умолчанию, `quality` для КК, `object` для возражений/ответа о мерах, `appeal-expert` для результатов возражений), нет активного маршрута, нет подписей РГ / подписи эксперта.

Удаление (`workflow.ts:deleteDocument`): только единственная неподписанная версия в статусе `Проект`, без зависимых документов; номера после удаления не переиспользуются (`documentSequence`).

### 2.4 Каталог документов и коды

### 3.4 Другие зафиксированные решения (влияют на модель бэкенда)

- **КК проверяет проекты до окончательного утверждения** (`full-process.md`): статус «Направлен на согласование КК» блокирует редактирование; после «Без замечаний» документ идёт на обычное согласование/утверждение; при замечаниях — v2 → повторный КК. Уже утверждённые документы совместимы с КК «без сброса статуса».
- **Два уровня КК** (№ 392, пп. 128–131): поле `level` «Первый уровень» / «Второй уровень» (20 раб. дней); эксперт не входит в аудиторскую группу; отдельный руководитель КК утверждает заключение. Централизованная месячная выборка второго уровня не реализована.
- **Назначение эксперта КК** — руководитель КК, отдельно на каждый этап; замена требует причины; при замене подписавшего эксперта создаётся новая версия без чужой подписи (`qualityAssignment.ts`).
- **Подтверждение КВГА** поручения (основного и встречного) — адресный подтверждающий, решение/возврат с причиной; новая версия не наследует подтверждение.
- **Подписи РГ**: задание — все участники версии РГ, завершает руководитель группы; отчёт — все участники, без отдельного финального утверждающего (`bpmn-main-stage`).
- **Основной этап** (`bpmn-main-stage`): отчёт создаётся и согласуется **до** реестра (иначе цикл); согласованный реестр → согласование доказательств → подтверждающий реестра → КК2 (подпись эксперта → руководитель КК → утверждение/возврат) → окончательное утверждение реестра, затем доказательств → параллельная отправка реестра и отчёта объекту → ознакомление → подпись объекта «Подписан» / «Подписан с возражениями» / «Отказ от подписания» (отказ фиксирует аудитор с основанием и подтверждением).
- **Заключение** заблокировано до подписи/отказа объекта; при возражениях — активный результат рассмотрения + повторный КК2, ссылающийся на версию результата (`creationBlock` для `conclusion`).
- **Предписание**: отменённые нарушения не переходят; частичная отмена уменьшает сумму в производных данных; исходный реестр не переписывается; без нарушений не создаётся.
- **Регистрация**: поручение нельзя направить объекту до регистрации УК (№ 413, п. 8); регистрация доп. поручения о приостановлении/возобновлении/отмене/продлении меняет `executionState`/`schedule`/`bases` и пишет историю дела; журнал регистрации — в карточке дела.
- **Дополнительное поручение → новые версии** связанных документов по явной команде (`applyAmendment`): вопросы, цель, объекты, сроки, риски, группа переносятся; старые подписи и версии сохраняются; повторное применение и применение к изменившимся версиям блокируются; после возражений или на заключительном этапе перенос блокируется.
- **Апелляция** (`follow-up`): объект подаёт возражения (дата и способ подачи; для почты — подтверждение даты); руководитель управления апелляции назначает исполнителя; комиссия фиксирует принятие/отказ (отказ → извещение объекта, без него заключение блокируется); аудитор готовит двуязычные обоснования по каждому пункту с файлами, подписывает руководитель подразделения; результаты проходят членов комиссии последовательно и председателя; отзыв до первого согласования; результат направляется объекту.
- **Третьи лица** (№ 392, п. 101-1): реестр уведомлений → получение → позиция → передача; можно обосновать отсутствие затронутых лиц.
- **Требования сведений** (`bpmn-implementation`): цикл раундов `sent → awaiting → received → review → accepted | rejected → resend | refused | overdue`; ответ объекта — не приёмка; встречное требование берётся на проверку отдельно; срок обязателен и в будущем; для встречного — автоматический отказ по истечении срока (по его BPMN).
- **Соавтор** назначается руководителем органа аудита; редактирование дела/документов — автор или соавтор.
- **Уведомления**: текущему участнику маршрута, эксперту КК, объекту; переход к документу, отметка прочтения; все сохранения — в истории дела.
- **Удаление**: только единственный неподписанный проект без зависимостей; номера не переиспользуются; прежние вложения защищены при доработке.
- **Рабочие формы** необязательны для КК (с 09.09.2026 по запросу заказчика; «не вывод об отмене требований стандартов»).
- **Не перенесено из BPMN намеренно** (`bpmn-implementation`, `bpmn-main-stage`): коды сигналов альтернативных КК, автозакрытие дела при отрицательном решении КВГА, автоподпись отчёта по таймеру (`signed_automatically` из `evga_doc_51`), альтернативные условия завершения, автоматический выбор маршрута КК2/КК КВГА (`qc_route` считался внешним сервисом, правила не переданы), реактивация реестра с обходом КК (`isReactivation`), «ошибочная запись статуса без возражений» в `Activity_0krfbhd`.
- **Совместимость данных**: новые версии приложения не мигрируют IndexedDB, только добавляют необязательные поля; демо-генераторы не перезаписывают пользовательские дела; legacy-маршруты мигрируются `migrateLegacyApprovalRoutes`.

## 5. Открытые вопросы, влияющие на проектирование бэкенда

Зафиксированы командой (`full-process.md`, `first-flow.md`, `npa-review`, `follow-up`, `bpmn-*`, `stand-checks.json`) и дополнены выводами из кода.

1. **Начальный статус дела**: «Открыто» (список, ФЛК) vs «Проект» (компактная карточка 1966:21332). Влияет на `CaseStatus`.
2. **Источник плановых дел**: ручной выбор из перечня (макеты) vs автоматическое получение из СУР/ФК (постановка). Нужен контракт «Перечень ОА» и его основания.
3. **Первый документ дела**: ФЛК — автосоздание программы; другой раздел — ИРПИ входной; ещё один — несколько документов сразу. Принято Q08 (ручное), но старая система (`EVGA_Create_Case_v4_Parallel_Docs`, `evga_doc_m18_m19_auto_create`) создавала документы автоматически — при переиспользовании n8n-логики нужно решить, кто прав.
4. **Формат номеров**: дела (`30101-YY-NNNNN`?), документов, версий, регистрации ЕРСОП; связь с внешними реестрами.
5. **Момент существования черновика поручения и условие открытия следующего этапа** (Q09).
6. **Доп. поручение**: при «Активный» или «Зарегистрирован» (Q10); полное версионированное распространение изменений на программу/задание/объекты с повторной регистрацией (не реализовано).
7. **Состав комплекта КК2/КК3** и допустимость согласования исправленного документа без повторного КК (Q13; `full-process`).
8. **Правило выбора маршрута КК2 / КК КВГА (`qc_route`)** — считалось внешним сервисом старой системы, правила не переданы.
9. **Предписание**: событие создания, обязательные документы (Q14).
10. **Кабинет объекта**: действующий вид «Общие сведения» (3 бледных PDF), момент появления документа, доступные действия (Q15); реальная модель представителя объекта (в prof — `User.is_subject_representative` + `subject`).
11. **Возражения**: связь результата с редакцией отчёта; приостановление/продление рассмотрения, дополнительные материалы, судебное обжалование, повторное открытие закрытого дела, самостоятельная апелляция по встречной проверке — не автоматизированы; 30 дней «нельзя считать окончательным».
12. **Ответ о принятых мерах**: кто создаёт (объект после уведомления или аудитор), несколько ответов на пункт (Q17).
13. **Завершение дела**: что блокирует и какие действия остаются после (Q18).
14. **Справочники**: вид проверки, основание/инициатор, сотрудники/штатное расписание, вопросы аудита, бюджетные программы, показатели, классификатор нарушений (Q19; в старой системе — `EVGA_Dictionaries`, `Control_Reasons_Type`, `Control_Spheres`, `Offense_Type`, `Risk_Category`, `Sampling_Methods` и т.д.).
15. **Печатные формы**: официальные бланки vs электронная карточка; серверная выгрузка (Q20).
16. **Талон-приложение ВП** — не предусмотрен НПА; применимость `counter-notification`.
17. **Иск о принудительной ликвидации палаты оценщиков** — форма временная.
18. **Административное производство** (M38–M57) — ПЗ не передано; в Figma есть 25 фреймов.
19. **Производственный календарь РК** — утверждённый источник переносов.
20. **Отражение результатов КК в классификаторе нарушений, итогов возражений и изменений доп. поручений в ранее утверждённых документах** — правила не подтверждены; изменённые поля не переписывают подписанные источники.
21. **Последовательность и параллельность подписания** — принято последовательное «пока»; контракт `shared/workflow` уже поддерживает `parallel` и `stages`.
22. **Раскрытие «ЭВГА»** и терминология «Секретно» vs «ДСП».
23. **Draft-страница Figma** (`3214:27559`, 199 фреймов) — содержит ли утверждённые изменения; вариант карточки дела (компактная 1966:21332 vs развёрнутая 10394:51016).
24. **Недостающие макеты**: 9179:48912 (требование ВП), 9179:56652 (акт воспрепятствования ВП), 403/404.
25. **Отдельно из кода**: `saveDocument` при регистрации доп. поручения «Отмена проверки» ставит `status = "Закрыто"`, а `counter-notification` при регистрации закрывает встречное дело — подтвердить у заказчика; `report` становится «Активный» в момент отправки объекту (не при утверждении) — нестандартный переход, требует подтверждения.

### 6.3 Рекомендация по точке интеграции

Фронт ЭВГА уже спроектирован под замену хранилища: `EvgaModule.tsx` получает `indexedDbCaseRepository` и передаёт в `useAuditCases(repository)`, который при каждом изменении вызывает `repository.save(cases)` целиком. Первый бэкенд-шаг с минимальными правками фронта — реализовать `ApiCaseRepository` с тем же контрактом (`GET/PUT /api/evga/cases/` всего набора). Это временно и небезопасно для многопользовательской работы (перезапись чужих изменений, base64-вложения). Целевой шаг — перенести чистые функции `workflow.ts`/`documentStateMachine.ts`/`preparationWorkflow.ts`/`mainWorkflow.ts` в Django-сервисы с action-эндпойнтами в стиле prof (`ApproveDocumentView`, `SendDocumentView`…), а фронт перевести с «локальный расчёт → save» на «вызов действия → перечитать дело». Тесты `tests/*.test.ts` (212 сценариев) — готовый список приёмочных сценариев для pytest.
